# AD-150 — secret-access covers every verb that prints a file, inline programs, and commands that print a stored secret

- **status**: active

## Decision

1. **`SECRET_READERS`** (`src/core/floor/floor.secrets.ts`) replaces the nine-verb reader list. It holds every
   verb that prints a file operand: `grep`/`egrep`/`fgrep`/`rg`/`ag`, `sed`, `awk`/`gawk`/`mawk`, `jq`/`yq`,
   `sort`, `uniq`, `cut`, `nl`, `tac`, `rev`, `diff`, `paste`, `column`, `fold`, `bat`, plus the existing `cat`,
   `head`, `tail`, `less`, `more`, `od`, `strings`, `xxd`, `base64`. Each operand is resolved and checked with
   `isSecretPath`, exactly as before.
2. **Inline programs.** For `python -c`, `node -e/-p/--eval`, `bun -e`, `deno eval`, `ruby -e`, `perl -e` and
   `php -r`, the program text is scanned for path-shaped runs. Each run is resolved against the project, and one
   that is a secret path refuses the command.
3. **Stored-secret commands.** A curated list of commands is refused by verb plus subcommand words, narrowed by
   the flag that makes them print the value where one exists. The list: `isys vault get`, `op read`/`item get`/
   `document get`, `security find-*-password -w|-g`, `kubectl get secret(s) -o`, `aws secretsmanager
   get-secret-value`, `aws ssm get-parameter(s) --with-decryption`, `gcloud secrets versions access`,
   `vault kv get`/`read`, `az keyvault secret show`, `gh auth token`, `pass show`, `keepassxc-cli show`,
   `doppler secrets get`, `heroku config:get`.

## Why

**A floor rule that one verb defeats is not a floor.** The rule's own catalog said "through a shell reader".
Measured against it, `grep . .env` printed the same file `cat .env` was refused for, and so did `sed`, `awk`,
`sort` and an inline `python3 -c`. The output rail masks some of those values afterwards, but only the ones it
recognises. The floor exists for the case where the input is known to be a credential file.

**Keeping a secret in a store is pointless if the agent can ask the store for it.** The local KeePass vault, a
password manager, a cloud secret manager and `gh` all exist so the value does not sit in a file or in a context
window. A command that prints it lands it in the transcript all the same.

**Patterns and scripts are still operands, and that is safe.** `grep -rn PASSWORD src` resolves `PASSWORD` to a
project path that is not a secret, and `src` is not one either. Only an operand that *is* a secret path trips the
rule, which is what keeps ordinary searches allowed in a rule with no switch.

## Trade-offs

**Recursive searches are not followed.** `grep -r key .` reads `.env` if it is in the tree, and the floor cannot
know that without touching the filesystem, which it never does. The output rail's known-value masking
([/decisions/ad-148.md](/decisions/ad-148.md)) covers what such a search prints.

**An inline program that merely mentions a secret path is refused** (`python3 -c "print('.env')"`), because the gate
reads text, not intent. Rare, and the remedy is a script file.

**The stored-secret list is curated, not exhaustive.** A CLI that is not on it is not refused, and `pass <name>`
(its implicit `show`) is not matched. Each addition is a row, with an allowed subcommand beside it in the tests.

**`kubectl get secret … -o name`** is refused with the rest of `-o`, though it prints only names.

## Not decided here

- Provider-declared secret paths, so a host's own credential or config file (one that holds API keys in plain
  text) is a secret path without core naming the host. This would be a `ProviderPort` addition, like
  `wiringTargets()` in [/decisions/ad-124.md](/decisions/ad-124.md).
- Copying a secret file to a non-secret name (`cp .env x && cat x`).
