# AD-147 — OpenCode V2 joins as a third provider, wired by a generated plugin file

- **status**: active

## Decision

1. **`ProviderWiring` gains a `file` strategy** (`src/contracts/wiring.ts`): `{ target, strategy: "file", entries,
   content, hostDir }`. The provider renders `content` in full. `bin/write-user-hooks.mjs` writes it, and refuses
   to overwrite a file at that path that does not carry the launcher marker unless `--force` is given.
   `tools/doctor.ts` reports it wired only while the file equals `content`. `tools/uninstall-runtime.ts` removes
   every registered provider's `file` target that carries the marker, read from the registry, so none of the three
   learns a provider name. `hostDir` decides whether the host is installed, because the file's own directory may
   not exist yet.
2. **`src/providers/opencode/`** targets OpenCode V2 (`@opencode/plugin` 2.x, verified against the source at tag
   `v2.1.4`). The V1 API (`@opencode-ai/plugin` 1.x, `tool.execute.before(input, output)`) is not supported: V2
   never dispatches those names.
3. **The wiring is a generated plugin**, `<config dir>/plugins/tlc-harness.js`, where V2 discovers plugins with no
   config edit. It is plain JavaScript importing only `node:child_process`. Each hook spawns
   `node <launcher> <handler>` asynchronously and pipes a JSON payload stamped `provider: "opencode"` and a
   dotted `hook_event_name`. The reply is applied to the live hook event:
   - `deny` → `throw`, which V2 turns into a failed tool call;
   - `rewriteInput` → replaces `input`;
   - `rewriteOutput` → replaces `result.content`;
   - `context` after a tool → appended to `result.content`;
   - `context` at session start → appended to `system` on every request of that session.
4. **`execute.before` fails closed.** A spawn error, a timeout or an unparseable reply throws. Every other hook
   fails open, as the launcher already does for the other hosts.
5. **Tool names are normalized in the adapter.** `shell`→`Bash`, `read`→`Read`, `edit`/`patch`→`Edit`,
   `write`→`Write`, `subagent`→`Task`, `webfetch`→`WebFetch`, `websearch`→`WebSearch`; `path`→`filePath`. Core
   keeps one spelling per tool.
   - `grep` maps to `read.before`, because it returns the lines of the file it searches.
   - A `<server>_<tool>` name is an MCP call.
   - A `patch` is checked once per file its text names.
   - The code-mode wrapper `execute` is skipped, because V2 fires the hook again for each inner call.
6. **`wiringTargets()`** is the plugin file plus `opencode.json` and `opencode.jsonc`, which decide which plugins
   load. The `wiring-tamper` floor rule ([/decisions/ad-124.md](/decisions/ad-124.md)) covers them with no floor
   change.
7. **`opencode` joins the vendor pattern** in `tools/dev/check-boundaries.ts`, so core and contracts cannot start
   spelling it.

## Why

**Neither existing strategy can express this host.**
- `replace` writes Cursor's hook document and `merge` writes Claude's settings block.
- OpenCode has neither. Its registration surface is a module exporting `{ id, setup }`.
- Adding a third vendor branch to install, doctor and uninstall would repeat the coupling
  [/decisions/ad-004.md](/decisions/ad-004.md) exists to prevent. A strategy keyed by shape keeps every new
  plugin-shaped host free.

**The bridge keeps core ignorant of the host.**
- Running the harness in-process would have meant importing core into OpenCode's Bun runtime and a second
  transport to test.
- The spawned launcher is the same process boundary the two existing hosts already cross, with the same
  fail-open runtime and the same hook trace.
- `spawn` and not `spawnSync`, because the plugin runs inside the OpenCode server and a synchronous child would
  stall every session on it.

**Fail closed at `execute.before` only.** That is the one hook whose silence lets an unchecked tool run. The same
choice is already made for Cursor's `preToolUse` and Claude's `PreToolUse` (`failClosed`).

**Normalizing names in the adapter, not core.** The floor's `READING_TOOLS`, the write rails and the spawn rails
all compare against `Read`/`Edit`/`Write`/`Task`. A third spelling there would have to be added in five places in
core and remembered in every future rail. One table in the adapter is the anti-corruption layer doing its job.

## Trade-offs

**No `ask` on this host.** A throw cannot ask anybody. `askSupportedOn` is empty, so `degrade` turns every ask into
a deny that says escalation was unavailable. `permission` `evaluate` could carry an ask, but answers OpenCode's own
permission prompt, not a tool call — not wired here.

**No stop grind, subagent lifecycle or compaction yet.**
- V2 has no hook that can keep a turn going. `session.idle` is only an event, and re-prompting from it is a new
  turn with different semantics.
- `contextAtStop` is false, so the stop rails abstain on this host rather than speak into nothing.

**A rewritten output replaces `result.content` and leaves the typed `result.output` as the tool produced it.** The
model reads `content`; a UI that renders `output` may still show the unmasked value. This is a narrower guarantee
than the transcript-level one Claude's `updatedToolOutput` already disclaims in
[/decisions/ad-124.md](/decisions/ad-124.md).

**Per-hook process cost.** Every tool call spawns the launcher, the same cost the other two hosts pay.

## Not decided here

- Supporting OpenCode V1 (`@opencode-ai/plugin` 1.x). It would be a second adapter or a second bridge export, and
  nothing here forecloses it.
- Grind via `ctx.event.subscribe` plus a re-prompt, `subagent.start`/`stop` from the `subagent` tool, `compact.before`
  from the `session` `compaction` hook, and session env through `shell` `create.before`.
- Treating `opencode.json` as a secret path. It holds provider API keys in plain text on many machines, but that is
  a floor change, argued on its own.
